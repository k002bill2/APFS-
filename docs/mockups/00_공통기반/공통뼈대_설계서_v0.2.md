## 0. 범위·원칙
- 대상: 6개 시스템(FFMS·RISK·REPORT·TRUST·BRIEF·모태펀드회계) **1개 URL 통합 포털**의 공통 기반.
- 원칙: **최소권한** · **신원 기반 접근통제** · **서버측 강제 + 감사**.
  - ⚠ **VPN 대체(폐지)**·**폐쇄형(익명 0)** 전제는 RFP/회의록과 상충·미결 소지 → **§12.1·§12.2** 참조(발주처 확인 전까지 확정 아님).
- RFP 정합: 표준프레임워크·KRDS(범정부 UI/UX)·KWCAG 2.2·CSAP 클라우드·시큐어코딩·개인정보 암호화/접속기록·**국정원 검증필 암호모듈**.

## 1. 사용자·신뢰경계 모델
- 사용자 **4종**: ①농금원 직원 ②운용사(GP) ③수탁기관 ④부처(농식품부·해수부).
- ⚠ **대국민/익명층**: 본 설계는 폐쇄형(4종)만 다루나, **RFP는 대국민 Front 페이지·방문자수/페이지뷰 통계·팝업/배너를 요구**(SFR-023, p.39·p.43)하고 회의록(정보화팀 06/30)도 대국민 서비스 도출을 언급. → **공개층(비로그인)을 별도 1개 층으로 추가**하고 본 공통뼈대는 그 뒤 **인증 업무포털**로 위치시켜야 함(§12.1-②).
- ⚠ **진입/VPN**: "공개 HTTPS 단일 포털 + VPN 폐지" 전제는 RFP에 근거 없음(VPN은 인프라 목록 p.20에만), 정보화팀 회의록은 오히려 *"웹으로 시스템 접속하는 VPN 계정 발급 예정"*. 또 투자관리부(06/02)는 **운용사 외부 직접접속 시 내부망/외부망 분리·외부접속 DB 분리**를 검토 대상으로 남김. → **최종사용자 접속 경로/망분리 발주처 확정 필요**(§12.2).
- 전 구간 HTTPS(중요정보 송수신 암호화, RFP p.61)는 확정.

## 2. 인증(로그인) 설계
| 사용자 | 1차 | 2차(의무) | 비고 |
|---|---|---|---|
| 농금원 직원 | ID/PW | 검증필 2차 인증(OTP) | **개별 계정**(부서 소속) |
| 운용사(GP) | ID/PW | 검증필 2차 인증(OTP) | **개별 계정** · 온보딩 시 간편인증(CI) |
| 수탁기관 | ID/PW | 검증필 2차 인증(OTP) | **개별 계정**(기관 소속) |
| 부처(공무원) | ID/PW | 검증필 2차 인증(OTP) | **개별 계정** · ⚠GPKI/행정전자서명 요구 확인(§12.1-①) |

> ⚠ **인증 수단 재검토(최우선)**: RFP는 *"ID/PW 인증 후 2차 인증"*(SFR-024, p.39)을 의무화하지만 **수단으로 OTP를 지정하지 않고**, ⓐ *간편인증*(로그인·회원가입·비번 재발급, p.39)과 ⓑ *"보안이 중요한 서비스…인증은 **전자서명 또는 행정전자서명 기반**"*(p.126)을 명시한다. 따라서 "2차=OTP만"은 우리 선택일 뿐 RFP 요건이 아니며, **전자서명/GPKI를 1차 범위 밖으로 둔 결정과 충돌**할 수 있다 → §12.1-①.

**계정 주체 모델 — 전원 담당자별 개별(개인) 계정, 공유 ID 없음:**
- **핵심 원칙**: 모든 사용자는 **담당자별 개별 계정**. 같은 아이디를 사람만 바꿔 물려쓰지 않음(감사추적·정보주체 요건). "법인 일을 개인으로 인증"하는 부담은 **본인확인(CI)을 붙이지 않는 것**으로 해소(공유 계정으로 해소하지 않음).
- ⚠ 단, RFP는 최종사용자 공유ID 금지를 **명시하지 않음**(공유금지 문구 p.99는 *용역 참여인력 보안서약* 대상). 해수부는 현재 **단일 ID 1개·사용자 1인**으로 운영(해수부 회의록 08/04). → 개별계정 전환은 **우리 개선안**(§12.3).
- **소속 구분**: 농금원=내부(부서), 운용사·수탁·부처=**기관 소속** 개별 계정. 권한·데이터 스코프는 소속(운용사·수탁사·계정구분) 기준 자동.
- **온보딩·본인확인 차이**:
  - **운용사** = 초대 온보딩 + **간편인증 CI·실명매칭**.
  - **농금원·수탁·부처** = **관리자 발급**(CI 미적용).
  - ⚠ RFP의 간편인증은 **전 회원 공통(자가 회원가입·자가 비번재발급)** 톤 → "운용사만 CI·초대 기반" 분기는 우리 설계(§12.3).
- **담당자 교체(수탁·부처 등)** = **구 계정 비활성 + 신 계정 신규 발급(온보딩)**. 같은 아이디 물려주지 않음.

**2차 인증(OTP) 구현 방식** — ⚠ SSO 제품 아님(외부 SSO 미도입 확정, 착수회의). 구현 옵션:
- **(A) 표준 TOTP 자체 구현(권장·저비용)** — 서버가 시드 생성·검증(HMAC은 **국정원 검증필 암호모듈**로), 사용자는 표준 authenticator 앱(Google/MS Authenticator 등). RFC 6238. 시드를 기관/개인에 바인딩.
- **(B) 팩터 대안** — SMS·이메일·앱 푸시·HW 토큰.
- **(C) 상용 OTP 전용 제품(검증필/CC)** — 예: 라온시큐어 TouchEn mOTP 등.
- **✅ 방향: (A) + 검증필 암호모듈.** 목업에 RFC 6238 실연(Web Crypto HMAC-SHA1) 탑재(30초 회전·허용창 ±1·시드 바인딩). ⚠ 배포 시 HMAC 연산·시드 저장 = **국정원 검증필(KCMVP) 암호모듈로 치환**(직접 제작 아님 — 검증필 획득 모듈을 JCE Provider로 도입해 API 호출).
- **검증필 암호모듈 = RFP 명시 요구**(p.126, PKI·DB암호화·구간암호화 등). SSO·DB암호화·DRM 채택 시 **보안기능확인서/CC인증 필수**(p.126) → 컴포넌트 적합성 검증 항목 관리(§12.5).
- **1차 인증은 provider 교체형(어댑터)** → 향후 GPKI/전자서명/통합인증 무중단 추가(전자서명 요구 대비 존치).

## 3. 계정 라이프사이클
**부트스트랩(최초 관리자·초기 셋팅)** — 첫 전산관리자는 초대/자기가입 불가 → **설치 시 DB 시드 1개 생성**(고정 계정명 `admin` 금지). 임시 비밀번호는 설치 담당자에게만, **최초 로그인 시 비밀번호 변경 + OTP 등록 강제** → 활성. 이후 이 계정이 나머지 사용자를 등록/초대. **개발/테스트**: 시드 계정 + 유형별 샘플을 DB 시드로 로드, 외부 의존(간편인증 CI·SMS·검증필 OTP)은 **모의(mock)**. (RFP 무규정 — 설계 판단, §12.3)

**온보딩(가입) — 운용사(초대 경로)**
1. 농금원 관리자가 초대 발송. 소스 = 운용사 전자보고 운용인력 명단(+최초는 부트스트랩).
2. 초대 이메일 = 농금원 보유 이메일(화이트리스트)로만 발송·검증.
3. 수신자 → 링크 → **간편인증(본인확인)** → **실명매칭**(CI ↔ 초대명 일치 시에만 활성, 불일치=거부+감사).
4. **초대 = 사전 승인** → 자동 활성. 소속·Role은 초대에 관리자가 지정(자기주장 금지).

**온보딩 — 농금원·수탁·부처(발급 경로)**: 관리자가 개별 계정 발급(이메일 필수) → 온보딩 안내 메일 → 대상이 링크 접속 → **① 비밀번호 설정 → ② OTP(QR) 등록 → 활성**. QR·비밀번호는 이메일이 아니라 링크 접속 후 화면에서만.

**오프보딩·담당자 교체**
- 운용사 인력변동(퇴사) 보고 → 계정 자동 비활성 + 정기 대사.
- 수탁·부처 담당자 교체 = 구 계정 비활성 + 신 계정 신규 발급(온보딩). OTP 재발급은 *동일인 기기변경/분실* 시만(계정 유지 + 새 QR 재등록).

**비밀번호·계정 보안**: ⚠ **아래 구체 수치는 「개인정보 안전성 확보조치 기준」 기반 제안값 — RFP는 수치 미규정**(§12.3):
- 정책(9자↑·영문·숫자·특수·90일 주기·재사용 금지) · 로그인 **5회 실패 → 잠금**(관리자 해제) · **만료 → 로그인 시 강제 변경**(+안내 메일) · **OTP 재발급**(분실/기기변경) · 세션 유휴 30분 · 유휴 90일 휴면.
- ⚠ **간편인증 셀프 비번재발급**은 RFP 명시 기능(p.39) → 보안 화면에 추가 필요(현재 관리자 재발급만, §12.5-①).

**상태관리**(RFP "회원상태 변경" p.39): 활성/온보딩대기/비활성/정지/잠금/유휴/말소. 모든 등록·초대·활성·상태변경·잠금해제·OTP 재발급 = 감사로그.

## 4. 권한 모델 — 2축 분리
> 메뉴(기능) 권한과 데이터 권한은 **완전 분리**한다.

**축1) 메뉴·기능 권한** — *ROLE 단위*, "사용 가능/불가"
- 기능 4종: **조회 · 인쇄·다운로드 · 등록/수정/삭제 · 관리자**. 인쇄·다운로드를 조회와 분리(반출 통제).
- **ROLE = 독립 관리 엔티티**(등록·복사·삭제·매트릭스). 삭제는 배정 0명일 때만.
- **사용자 ↔ ROLE = N:M** → **유효 권한 = 합집합**(겸직 반영).
- **신규 메뉴는 ROLE에만 반영 → 해당 ROLE 전 사용자 자동 적용**.
- ⚠ 데이터 스코프(축2)는 ROLE이 아니라 **사용자 구분·소속**으로 결정 — 두 축 독립.

**축2) 데이터 스코프** — *자펀드 마스터에서 자동 파생*
| 사용자 | 규칙 | 유형 |
|---|---|---|
| 농금원 | 전체 (기본필터 `담당자=나`, 해제 가능) | 소프트 |
| 운용사 | `업무집행조합원(GP) = 내 소속` | 하드 |
| 수탁 | `주수탁 = 내 소속` | 하드 |
| 부처 | `계정구분 = 내 부처(농식품/수산)` | 하드 |

- 자펀드 등록 시 운용사·수탁·계정구분·담당자 입력이 곧 데이터 권한 세팅. 회의록(투자관리부 06/02) *"자펀드관리에서 담당자 코드 기준으로 알림·권한 동작"*이 이를 뒷받침.

| 사례 | 관계 | 열람 | 보고(WRITE) |
|---|---|---|---|

| 수탁(주/부) | 주수탁 (1:1) | **주수탁만** (부수탁=사용자 아님) | 주수탁만 |

## 6. 접근제어·감사
- **UI 숨김만으론 불충분** → 모든 요청 **서버측 인가**: ①메뉴권한 검사 ②**데이터 요청마다 스코프 강제**(IDOR 방어).
- 위반 시 차단 + "비정상 접근" 감사로그 (+반복 시 관제/잠금). RFP: 웹취약점·시큐어코딩 broken access control(p.60).
- **감사/기록**: 개인정보 **접속기록 5항목**(계정·일시·IP·정보주체·수행업무) **2년**, **권한변경이력 3년** — **RFP p.62와 정확히 일치**(§12.4). 「접속기록 점검 가이드라인」·「정보시스템 접근권한 관리 규정(국무총리훈령)」 준거(p.62·p.112).

## 7. 개인정보·암호화 (검색여부로 방식 분리)
| 필드 | 방식 | 이유 |
|---|---|---|

## 12. RFP·회의록 원문 대조 점검 결과 (2026-08-26)
> 방법: RFP PDF 전문 재추출(PyMuPDF, CID 폰트로 pdftotext 누락 → 페이지=PyMuPDF 기준) + 회의록 9건 전문. 인용은 원문. 목적 = **본 설계가 RFP/회의록과 어긋나는 지점 식별**.

### 12.1 🔴 상충 (재검토 필요)
**① 인증 수단 — 우리 "2차=OTP만·전자서명 defer" vs RFP "전자서명/행정전자서명 기반 + 간편인증"**
- RFP p.126: *"보안이 중요한 서비스 및 데이터의 접근에 관련된 사용자 인증은 **전자서명 또는 행정전자서명을 기반으로 하여야 한다**"*(적용 ○), 근거법령에 전자서명법·행정전자서명 인증업무지침.
- RFP p.39: *"ID/Password 인증 후 **2차 인증**"*(의무·지지) + *"**간편인증** 후 회원가입"*, *"비밀번호 분실 시 **간편인증** 절차 후 랜덤 비밀번호 제공"*.
- 판단: 2차 인증 의무는 지지되나 **수단으로 OTP는 미지정**. RFP는 전자서명·간편인증을 명시 → "OTP만"은 우리 선택. **전자서명/법인인증서를 1차 범위 밖으로 둔 결정(§10-1)이 p.126과 충돌** 가능.
- 조치: ⓐ 발주처에 "OTP로 2차 충족 가능한지 / 전자서명 필수인지" 확인. ⓑ §2 1차 인증 어댑터에 **GPKI/전자서명 연동 지점 유지**(보류→연동 예정). ⓒ 사용자 defer 결정을 이 근거와 함께 재확인.

**② 사용자 범위 — 우리 "폐쇄형·대국민 없음" vs RFP "대국민 Front·방문통계"**
- RFP p.43: *"**대국민 대상**의 친화적이며 차별화된 **Front 페이지**"*, p.39: *"접속 통계 – **방문수, 일·주·월별 방문자수, 페이지뷰**"*, 팝업/배너. 회의록(정보화팀 06/30) 대국민 서비스 도출·등급변경 가능성.
- 조치: 아키텍처 **2층화 — 공개층(비로그인 홈·공지·통계) + 인증 업무포털(4종)**. 본 공통뼈대=후자.

### 12.2 🟡 미결·확인 필요
- **VPN(§1)**: RFP에 VPN 폐지 근거 없음(인프라 목록 p.20에만). 정보화팀 회의록 *"웹으로 시스템 접속 VPN 계정 발급 예정"*. → 최종사용자 VPN 없이 공개 HTTPS 전제 확인.
- **운용사 외부 직접접속(§1)**: 투자관리부(06/02) *"URL 직접 신청·접수 미확정, 도입 시 외부접속 DB 분리·내부망/외부망 분리·법인 인증서/전자서명 필요"*. → 단일 통합 vs 분리 아키텍처 확정.
- **권한 등급 세분(§10-1)**: UIUX(07/23)가 관리자/실무자/조회자 적극 제안 → defer 유지 재확인.

### 12.3 ⚪ 무근거 — 우리 설계 판단(RFP·회의록에 규정 없음)
- **비번/세션 수치(§3)**: RFP는 *단방향 암호화*·*세션 종료*·안전성확보조치 기준 준수만, **수치 전무**. 9자·90일·5회·30분·90일 = 제안값.
- **부트스트랩(§3)**: RFP 무언급. 순수 설계.
- **공유ID 폐지·전원 개별계정(§2)**: RFP는 최종사용자 공유금지 명시 안 함(p.99=용역인력 보안서약). 해수부 현재 단일ID. 개별계정=개선안.
- **담당자 교체 방식(§3)**: RFP는 계정 상태관리·이력만(p.39·62). 교체=비활성+신계정은 설계 판단.
- **K/J/M 구체 구현**: 방향은 지지, 자동파생·N:M 합집합·blind index 세부는 설계.

### 12.4 ✅ 지지 (근거 확실)
- 6개→1 URL(p.4~5) · 2차 인증 의무(p.39) · 전 구간 HTTPS(p.61) · 외부 SSO 미도입(착수회의) · RBAC 2축·서버측 인가·운용사 자사만(p.33·38·48·60) · **검증필 암호모듈**(p.126) · 단방향 비번(p.39) · **접속기록 2년·권한변경 3년(p.62 정확 일치)** · 담당자 코드 기준 권한(투자관리부).

### 12.5 ➕ 놓쳤을 RFP 요구 (반영 권장)
1. **간편인증 셀프 비번재발급**(p.39) — 현재 관리자 재발급만 → 자가 재발급 흐름 추가.
2. **접속기록 조회/통계 화면**(필수항목까지 p.62) — 자체구현 불가 시 접속기록 솔루션.
3. **회원 상태 라이프사이클(허가/강제탈퇴/유휴회원)**(p.39).
4. 채택 컴포넌트(SSO·DB암호화·DRM) **보안기능확인서/CC인증 적합성**(p.126).
5. 시큐어코딩·웹취약점 진단·웹접근성 인증마크(p.40·43·60).
